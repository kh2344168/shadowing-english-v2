# نسخ تقدّم الطلاب داخل SQL عند إعادة النشر — #7 و#25

التاريخ: 24 أكتوبر 2026. تحسين جزئي.

كان الناشر يقرأ كل صفوف تقدّم المجموعة إلى ذاكرة الـAPI، ثم يُنشئ نسخًا
جديدة عبر EF. على SQL Server صار يستخدم `INSERT ... SELECT` داخل المعاملة
نفسها، مع خريطة معرفات الدروس وقائمة المراحل التي لم يتغير محتواها.
يبقى مسار SQLite الصغير لاختبارات العقد كما كان. لا يغير التعديل قرار
حمل التقدّم للمراحل المتغيرة أو شروط رؤية الطالب للنسخة المنشورة.

نجح بناء Release وخمس حالات `--ai-publication-check`. اختبرنا قاعدة SQL
معزولة ومخرج WhisperX محلي حقيقي:

| الحمل | زمن إعادة النشر | زيادة ذاكرة العملية المقاسة | النتيجة |
| --- | ---: | ---: | --- |
| 30 مجموعة، درس واحد، 3000 طالب و30000 محاولة | 6172 ms | 6 MB | نجح النقل |
| 30 مجموعة، 10 دروس، 3000 طالب و30000 محاولة | 8100 ms | 11 MB | نُقل تقدّم كل درس ومحاولاته إلى الدرس الصحيح |

اختبار SQL إضافي بثلاث مجموعات ودرسين أضاف تقدّمًا قديمًا لمرحلة غير مفعلة.
بقي في النسخة القديمة ولم ينتقل إلى النسخة الجديدة، بينما انتقل تقدّم
الـShadowing الصحيح. نجح الاختبار في 422 ms دون أخطاء.

القياسان تشغيل واحد لكل حمل، ولا يثبتان زمنًا مضمونًا. القياس السابق
للمنهج ذي 10 دروس كان بين 9816 و11881 ms، لكنه أُجري في ظروف مختلفة.
التحسن المؤكد من الكود هو تجنب تحميل آلاف صفوف التقدّم وتتبعها في EF؛
خطر تضخم تاريخ المحاولات مع كل إعادة نشر ما زال قائمًا. اختبار SQL أضاف
بيانات إلى قاعدة الاختبار المعزولة ولم يحذف بيانات أو ملفات المستخدم.
